## Focus
Stabilize locksmith ops dashboard (tabs + CRM stub)

## Steps
1. Locate the dashboard entrypoint (e.g., `src/pages/Dashboard.*` or `src/app/dashboard/*`) and map current routes/components.
2. Implement a stable tab system:
   - Define tab IDs + labels (`Overview`, `Jobs`, `Customers`, `Settings`).
   - Add a tab bar component and wire it to routing or local state (choose one; prefer URL-driven tabs).
3. Add a CRM stub behind the **Customers** tab:
   - Create a minimal customer list view with mocked data (name, phone, last job, notes).
   - Add “Add customer” button that opens a modal with a non-persisted form (validate required fields only).
4. Add a lightweight in-memory data layer:
   - `src/lib/mockCrm.ts` exporting `getCustomers()`, `createCustomer()`.
   - Keep signatures compatible with later backend swap.
5. UX + stability pass:
   - Loading/empty states for each tab.
   - Basic error boundary or try/catch around data calls.
   - Ensure tab switching doesn’t lose state unexpectedly (define expected behavior).
6. Smoke test:
   - Run the app, click through tabs, create a mock customer, confirm list updates.
   - Fix any console errors/warnings introduced.

## Files to Touch
- Dashboard route/page component (e.g., `src/pages/Dashboard.tsx` or `src/app/dashboard/page.tsx`)
- Tab UI component (new: `src/components/DashboardTabs.tsx`)
- CRM stub view (new: `src/components/CustomersTab.tsx`)
- Mock CRM data layer (new: `src/lib/mockCrm.ts`)
- Styles if needed (e.g., `src/styles/dashboard.css` or component-level styles)

## Risks / Notes
- If routing structure is unclear (Next.js app router vs React Router), tab implementation choice changes—confirm early.
- Avoid overbuilding CRM: keep it strictly mock/in-memory, but design function signatures to match future API.
- Define “state retention” rule upfront (URL tab param + minimal local state is usually safest).
